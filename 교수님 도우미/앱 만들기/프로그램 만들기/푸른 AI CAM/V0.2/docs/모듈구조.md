# 푸른 AI CAM 모듈 구조와 연결 규칙 (V0.2)

> 목적: 기능을 고칠 때 **해당 모듈과 이 문서만 읽고** 작업할 수 있게 한다 (전체 코드 반복 분석 방지).
> 사용자는 하나의 HTML 파일만 실행한다. 내부 소스는 기능별 파일로 나뉘어 있고 `node build.mjs`가 단일 HTML로 자동 통합한다.

## 1. 파일 구조와 역할

```
src/
├─ modules.json            ← 로드 순서 (빌드·테스트 공용, 유일한 목록)
├─ load-node.cjs           ← Node 테스트용 로더 (modules.json 순서로 로드)
├─ template.html, style.css   통합 화면 뼈대·공통 디자인·반응형
├─ engine/                 [공통 엔진]
│  ├─ common.js            버전·상수·숫자 유틸·재질/나사 표·소재 좌표계·공구/장비 기본값·기하 계산
│  ├─ project.js           프로젝트·공정·공정 묶음 정규화(외부 JSON 방어), 그룹 대표 직경
│  └─ patterns.js          홀 배열(직선·사각·PCD)·입력값 검사·구멍 순서(최단·지그재그)
├─ ops/                    [가공 모듈] — 가공 종류별 계산·검증·표준 가공 데이터
│  ├─ registry.js          가공 모듈 등록소 + 표준 규격 + 호출 위임
│  ├─ hole-common.js       홀 계열 공통: 깊이·참고 조건·추천·공통 검증·정의 도우미
│  ├─ center.js drill.js peck.js deep.js   센터·일반·고속 펙(G73)·심공(G83)
│  ├─ tap-common.js        탭 계열 공통: 피치·기초 드릴·탭 깊이 검증
│  ├─ tap.js rigid.js      일반 탭(G84)·리지드 탭(M29+G84)
│  └─ planned.js           개발 예정: 평면·사각 포켓·원형 포켓·외곽 윤곽 (선택 불가)
├─ process/plan.js         [공정 관리] 묶음 적용·저장·적합성, 공구 교환 최소화 정렬, 병합, 구멍 순서,
│                          표준 가공 데이터(toolpath)·공구 교환 표시(toolChange)
├─ post/                   [포스트프로세서]
│  ├─ registry.js          제어기 등록소 + generateNC 진입점 (미지원 제어기·사이클 차단)
│  └─ fanuc.js             FANUC 0i/31i 변환 (미쓰비시·지멘스는 'planned' 등록만)
├─ verify/                 [검증 모듈] — 생성 코드와 독립
│  ├─ model.js             입력값 11개 항목 검증 (공통 항목 + 가공 모듈 validate 호출)
│  └─ nc-fanuc.js          독립 NC 해석기: 문법·모달·경로·충돌·탭 이송·기초 구멍·조건 + 교차 비교
└─ ui/                     [화면]
   ├─ storage.js           [저장 모듈] localStorage·초기 데이터·손상 복구·관리자 해시 도구
   ├─ graphics.js          [그래픽 모듈] 좌표 변환·화면 맞춤·그리기
   └─ app.js               [통합 화면] 5분할 화면·입력·설정·관리자·공유·버전
```

## 2. 데이터 흐름

```
입력(화면) ─▶ 프로젝트 데이터(engine) ─▶ 가공 모듈 계산·검증(ops) ─▶ 공정 계획(process)
                                                                          │ 표준 가공 데이터
                                                                          ▼
         NC 다운로드 ◀─ 차단 판단(ui) ◀─ 독립 NC 검증(verify/nc) ◀─ 포스트프로세서(post)
                              ▲
                              └── 모델 검증 11항목(verify/model)
```
- **가공 모듈은 G코드를 만들지 않는다.** `toolpath()`가 `{ kind: 'peck', … }` 같은 표준 데이터만 돌려준다.
- **공구 교환·공정 간 안전 이동**은 공정 관리(`toolChange`, `first`, `last`)와 포스트프로세서의 공통 블록에서만 처리한다.
- **사용자가 정한 그룹 안의 공정 순서는 바꾸지 않는다.** 공구 교환 최소화 정렬이 그룹 내부 순서를 바꾸게 되면 자동으로 "그룹 순서대로"로 되돌리고 안내한다.
- **검증기는 포스트프로세서 코드를 쓰지 않는다** (공통 유틸과 참고 절삭 조건표만 공유). 생성된 NC는 생성기 계산값과 구멍 단위로 교차 비교한다.

## 3. 가공 모듈 표준 규격 (ops/registry.js)

| 항목 | 설명 |
|---|---|
| `id` | 고유 이름 (프로젝트 파일에 저장). 바꾸면 기존 파일 호환이 깨지므로 변경 금지 |
| `label`, `code`, `ncName` | 화면 이름, 화면 표시 코드, NC 주석용 영문(ASCII) |
| `stage` | 공구 교환 최소화 정렬 단계 (1 센터 → 2 드릴 → 3 탭) |
| `role`, `toolTypes` | 계열 역할(spot/drill/tap), 사용 가능한 공구 종류 |
| `defaults`, `ui` | 새 공정 기본값, 화면 입력 항목(q·dwell·thru·depthMode) |
| `depth()`, `ref()`, `recommend()`, `conditions()` | 깊이, 참고 조건, 추천 조건, 실제 S·F |
| `validate(ctx)` | 모듈 전용 검증. `ctx.add(level, 항목번호, 메시지)` |
| `toolpath(params)` | 표준 가공 데이터 `{ kind, spindle }` (z·r·q·dwell·feed·rpm 은 공정 관리가 채움) |
| `status` | `'ready'` 또는 `'planned'` (planned 는 목록에만 표시, 선택·저장 불가) |

필수 항목이 빠지거나 id 가 중복되면 등록 단계에서 오류가 난다 (테스트로 확인).

### 새 가공 모듈 추가 절차
1. `ops/새모듈.js` 파일 작성 → `P.OPS.register({...})` (홀 계열은 `HOLE.defineHoleOp` 사용)
2. `src/modules.json` 의 `core` 목록에서 `ops/planned.js` 앞에 추가
3. 새 사이클 종류(`kind`)가 필요하면 해당 포스트프로세서의 `CYCLE` 표와 `kinds` 에 추가하고, 독립 검증기에 해석 규칙을 추가
4. `tests/` 에 모듈 단위 테스트 추가 → `node --test tests/*.test.cjs`, `node build.mjs`, `node tests/e2e.cjs`
5. 평면·포켓·윤곽처럼 **G01/G02/G03 공구 경로가 필요한 모듈**은 현재 독립 검증기가 절삭 이동을 검증하지 못하므로(경고·차단), 검증기 확장이 먼저 필요하다.

## 4. 포스트프로세서 표준 규격 (post/registry.js)

| 항목 | 설명 |
|---|---|
| `id` | 장비 설정의 제어기 값 (`machine.control`) |
| `kinds` | 지원하는 표준 사이클 종류. 계획에 지원하지 않는 종류가 있으면 생성 차단 |
| `generate(project, machine, plan, opts)` | `{ text, hits }` 반환. `hits` = 구멍별 `{ t, x, y, z, r, code }` |
| `verifier` | 같은 제어기용 독립 NC 검증기 이름 (`PCAM.NCV`) — 없으면 NC 출력 불가 |

### 새 제어기 추가 절차 (예: 미쓰비시)
`post/fanuc.js` 를 복사해 `post/mitsubishi.js` 로 만들고 차이(고정 사이클·리지드 탭 지령·주석 규칙)를 반영 → `verify/nc-mitsubishi.js` 검증기 작성 → `modules.json` 등록 → 실장비 검증. **검증기 없이 포스트만 추가하면 출력이 차단된다.**

## 5. 수정 시 영향 범위

| 수정 대상 | 영향 | 필요한 테스트 |
|---|---|---|
| 가공 모듈 1개 (예: `ops/peck.js`) | 그 가공 방식만 | 단위 테스트 전체 + 해당 모듈 테스트 |
| `ops/hole-common.js`, `ops/tap-common.js` | 홀 계열 6개 전체 | 전체 단위 + 전후 비교 + 화면 |
| `engine/*` (공통 엔진) | **전체 기능** | 전체 단위 + 전후 비교 + 화면 (필수) |
| `post/fanuc.js` | FANUC 출력 전체 | 전체 단위 + 전후 비교(의도한 변경 명시) + 화면 |
| `verify/*` | 차단 판단 전체 | 결함 주입 테스트 + 무작위 정상 프로젝트 통과 확인 |
| `ui/*` | 화면만 (계산 결과 불변) | 화면 통합 테스트 |
