> **V0.7 화면 규칙** (`src/ui/app.js`, `src/template.html`, `src/style.css` 만 변경 — 엔진 모듈은 V0.6 과 같음, `tests/regression-v06.test.cjs` 가 확인)
> - 가공 입력 양식(`specForm`·`pocketForm`·`contourForm`·`faceForm`·`chamferForm`)은 문자열 대신 `{ basic, opt, optSum, adv, advSum, res }` 를 돌려준다. `basic` = 항상 보임, `opt`·`adv` = 접힌 줄 내용, `*Sum` = 줄에 보이는 현재 값 요약, `res` = 자동 구성 결과.

## 2. 데이터 흐름

```
입력(화면) ─▶ 프로젝트 데이터(engine) ─▶ 가공 모듈 계산·검증(ops) ─▶ 공정 계획(process)
                                                                          │ 표준 가공 데이터
                                                                          ▼
         NC 저장 ◀─ 차단 판단(ui) ◀─ 독립 NC 검증(verify/nc) ◀─ 포스트프로세서(post)
                              ▲                    │ 이동 목록(motions)
                              │                    ▼
                              │        시뮬레이션(sim) ─▶ 3D 화면(ui/view3d)·예상 시간
                              └── 모델 검증 11항목(verify/model)
```
- **3D 시뮬레이션은 생성기의 내부 값이 아니라 독립 검증기가 실제 NC 문장을 해석한 이동 목록으로 만든다.** 화면에 보이는 것은 저장되는 G코드 그대로이다.
- 밀링 허용 영역(`pocketRegions(project, machine)`)은 각 가공 모듈의 `regions()` 로 모델 데이터에서 따로 계산해 검증기에 전달한다.
  - 종류: 사각/원형 포켓, `area`(자유 형상+섬), `outside`/`inside`(윤곽·모따기), `face`(평면)
  - 검증기는 Clipper 를 쓰지 않고 자체 다각형 판정(`pip`·`edgeDist`)으로, 소재 아래 절삭 이동의 공구 중심이 영역 안에서 공구 반경(모따기는 깊이별 유효 반경) 이상 떨어져 있는지 확인한다.
- **[V0.5] 밀링 모듈 규격 추가 항목**:
  - `mill`: 'pocket' | 'contour' | 'face' | 'chamfer'
  - `moves(step, tool, 위치, machine, project)`: 공구 중심 이동 목록 `{g:0|1|2|3, x, y, z, f, i, j}`
  - `regions(op, 위치, stock, tool)`: 검증기용 허용 영역
  - `normalize(n, o)`: 모듈 전용 매개변수 정규화 (외부 파일 방어)
  - `ncUnit`: NC 주석 단위 이름

### 자유 형상 포켓에 남는 살이 없는 이유 (clearRegion)
- 첫 경로 L₁ = 영역을 (공구 반경 r + 측벽 여유)만큼 안쪽으로 오프셋한다. 다음 경로는 L₁ 을 간격 s(≤ 0.95r) 씩 안쪽으로 오프셋한 것이다. 이 경로들을 안쪽(잎)부터 모두 돈다.
- 어떤 점 q 가 L_k 영역 안에 있을 때:
  - L_k 경계에서 r 이내면 L_k 를 도는 공구에 깎인다.
  - r 보다 멀면 s < r 이므로 q 는 L_{k+1} 영역 안에 있다.
  - 마지막(잎) 영역에서는 경계까지 거리가 s(< r) 이하이므로 반드시 깎인다.
- 따라서 공구가 닿을 수 있는 모든 점(영역을 r 로 줄였다가 r 로 넓힌 부분)이 깎인다. 이는 무작위 60건 높이맵 시험으로 확인했다.
- **가공 모듈은 G코드를 만들지 않는다.** `toolpath()`가 `{ kind: 'peck', … }` 같은 표준 데이터만 돌려준다.
- **공구 교환·공정 간 안전 이동**은 공정 관리(`toolChange`, `first`, `last`)와 포스트프로세서의 공통 블록에서만 처리한다.
- **사용자가 정한 그룹 안의 공정 순서는 바꾸지 않는다.** 공구 교환 최소화 정렬이 그룹 내부 순서를 바꾸게 되면 자동으로 "그룹 순서대로"로 되돌리고 안내한다.
- **검증기는 포스트프로세서 코드를 쓰지 않는다** (공통 유틸과 참고 절삭 조건표만 공유). 생성된 NC는 생성기 계산값과 구멍 단위로 교차 비교한다.

### [V0.5 2차] 포켓 단계·진입·측벽 형상
- **단계** (`ops/pocket.js` `stageOf`): 각 단계는 앞 단계 여유(pw·pf)와 자기 여유(aw·af), 깊이 단 목록 `{ z, wall }` 을 가진다.
  - 황삭 → (중삭) → 바닥 정삭 → 측벽 정삭(또는 한 번에 정삭) → (측벽 형상).
  - `leaveOf` 로 바로 앞 같은 포켓 공정이 남긴 여유와 이 공정의 앞 단계 여유가 같은지 검증한다 (다르면 차단).
  - 측벽만 깎는 단(`wall`)은 앞 단계가 비운 곳에서 이송 하강 → 측벽 루프 → 다시 안쪽 (`mill-common.js` `wallPasses`, 자유 형상은 최근접 쌍 + 허용 영역 직선 검사).
- **진입**: 헬리컬 최소 반경 = 공구 반경 25%. 작은 잎은 부모 영역의 가장 넓은 곳에서 헬리컬, 그것도 안 되면 넓은 조상 윤곽 램프. 따로 떨어진 아주 작은 영역은 깎지 않고 경고한다. 선가공 구멍은 `drill` 공정의 `at` 오프셋.
- **측벽 형상** (`profOff`): 높이별 벽 위치 = −u·tan(구배) + 입구 R 원호 − 바닥 R 원호. 아래로 갈수록 안쪽으로만 가므로(단조) 평 엔드밀을 위에서부터 계단식으로 내리면 과삭이 없다. 다른 단계는 `profInset`(가장 안쪽 거리)만큼 더 안쪽에서 가공한다.
- **검증기** (`verify/nc-fanuc.js`): 생성기 코드를 쓰지 않고 `wallShift` 로 같은 식을 따로 계산해, 공구 바닥 높이의 벽 위치로 과삭을 판정한다.
  - 하강 구간(헬리컬·경사 포함)의 XY 폭이 공구 지름 25% 미만이면 사실상 수직 하강으로 차단한다 (선가공 구멍 안이면 허용).
  - 깎인 깊이(`clearedTo`)는 공구 자국 하나 또는 여러 자국의 합(37점 표본)으로 판정한다.
- **NC 줄 수**: 자유 형상 황삭은 원호 근사 허용 0.02mm, 안쪽 루프 점 줄이기(편차 0.01mm 이하, 최종 벽 루프 제외).

## 3. 가공 모듈 표준 규격 (ops/registry.js)

| 항목 | 설명 |
|---|---|
| `id` | 고유 이름 (프로젝트 파일에 저장). 바꾸면 기존 파일 호환이 깨지므로 변경 금지 |
| `label`, `code`, `ncName` | 화면 이름, 화면 표시 코드, NC 주석용 영문(ASCII) |
| `stage` | 공구 교환 최소화 정렬 단계 (1 센터 → 2 드릴 → 3 탭) |
| `role`, `toolTypes` | 계열 역할(spot/drill/tap), 사용 가능한 공구 종류 |
| `defaults`, `ui` | 새 공정 기본값, 화면 입력 항목(q·dwell·thru·depthMode) |
| `depth()`, `ref()`, `recommend()`, `conditions()` | 깊이, 참고 조건, 추천 조건, 실제 S·F |
| `validate(ctx)` | 모듈 전용 검증. `ctx.add(level, 항목번호, 메시지)` |
| `toolpath(params)` | 표준 가공 데이터 `{ kind, spindle }` (z·r·q·dwell·feed·rpm 은 공정 관리가 채움) |
| `status` | `'ready'` 또는 `'planned'` (planned 는 목록에만 표시, 선택·저장 불가) |

필수 항목이 빠지거나 id 가 중복되면 등록 단계에서 오류가 난다 (테스트로 확인).

### 새 가공 모듈 추가 절차
1. `ops/새모듈.js` 파일 작성 → `P.OPS.register({...})` (홀 계열은 `HOLE.defineHoleOp` 사용)
2. `src/modules.json` 의 `core` 목록에서 `ops/planned.js` 앞에 추가
3. 새 사이클 종류(`kind`)가 필요하면 해당 포스트프로세서의 `CYCLE` 표와 `kinds` 에 추가하고, 독립 검증기에 해석 규칙을 추가
4. `tests/` 에 모듈 단위 테스트 추가 → `node --test tests/*.test.cjs`, `node build.mjs`, `node tests/e2e.cjs`
5. G01/G02/G03 공구 경로가 필요한 모듈(포켓 등)은 `toolpath()` 가 `{ kind: 'path' }` 를 돌려주고, 이동은 `pocketMoves` 처럼 공구 중심 기준 이동 목록으로 만든다. 독립 검증기가 소재 아래 절삭을 허용하려면 **허용 영역(포켓 영역과 같은 것)을 모델 데이터에서 계산해 검증기에 넘겨야** 한다. 허용 영역이 없는 절삭은 차단된다.

## 4. 포스트프로세서 표준 규격 (post/registry.js)

| 항목 | 설명 |
|---|---|
| `id` | 장비 설정의 제어기 값 (`machine.control`) |
| `kinds` | 지원하는 표준 사이클 종류. 계획에 지원하지 않는 종류가 있으면 생성 차단 |
| `generate(project, machine, plan, opts)` | `{ text, hits }` 반환. `hits` = 구멍별 `{ t, x, y, z, r, code }` |
| `verifier` | 같은 제어기용 독립 NC 검증기 이름 (`PCAM.NCV`) — 없으면 NC 출력 불가 |

### 새 제어기 추가 절차 (예: 미쓰비시)
`post/fanuc.js` 를 복사해 `post/mitsubishi.js` 로 만들고 차이(고정 사이클·리지드 탭 지령·주석 규칙)를 반영 → `verify/nc-mitsubishi.js` 검증기 작성 → `modules.json` 등록 → 실장비 검증. **검증기 없이 포스트만 추가하면 출력이 차단된다.**

## 5. 수정 시 영향 범위

| 수정 대상 | 영향 | 필요한 테스트 |
|---|---|---|
| 가공 모듈 1개 (예: `ops/peck.js`) | 그 가공 방식만 | 단위 테스트 전체 + 해당 모듈 테스트 |
| `ops/hole-common.js`, `ops/tap-common.js` | 홀 계열 6개 전체 | 전체 단위 + 전후 비교 + 화면 |
| `engine/*` (공통 엔진) | **전체 기능** | 전체 단위 + 전후 비교 + 화면 (필수) |
| `post/fanuc.js` | FANUC 출력 전체 | 전체 단위 + 전후 비교(의도한 변경 명시) + 화면 |
| `verify/*` | 차단 판단 전체 | 결함 주입 테스트 + 무작위 정상 프로젝트 통과 확인 |
| `ui/*` | 화면만 (계산 결과 불변) | 화면 통합 테스트 |
